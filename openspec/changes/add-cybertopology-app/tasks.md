- [x] 2.2a Meshlet render path on mesh-shader hardware (A14/M1+) behind the 2.2 `TargetRenderPath` seam + multi-million-triangle @60fps device acceptance — DONE via `add-meshlet-target-path` (spec: viewport-rendering). **Measurement-led, and the measurement changed the plan twice.** (1) The task assumed the acceptance needed meshlets; the existing indexed path was never tested at scale, so task 0 measured it first — synthetic tiles said 11.66 ms at 2732×2048 (comfortably inside budget), but a REAL asset said 16.54 ms for FEWER triangles. Uniform tiles overstate throughput by ~42% (perfect cache locality, uniform triangle size), so judging on the synthetic number would have closed this gate on a measurement that does not describe a scan. (2) That real-asset run had a compliant AVERAGE beside a 19.65 ms worst frame — a dropped frame at 60 Hz — so the acceptance criterion itself was wrong: it now gates on the worst frame, not the average alone. **Shipped:** engine patch 0007 clusters the RENDER STREAMS (not `Mesh` topology, so cluster indices address the same array the position buffer uses) with conservative bounding spheres and normal cones, asserted to CONTAIN what they claim — a too-tight bound culls visible geometry, which shows as holes rather than crashes. `MeshletRenderPath` (object/mesh shader pair) does vertex reuse + frustum culling; `availableKind` returns `.meshlet` on capable hardware and the renderer falls back if the pipeline will not build, with `unavailabilityReason` saying why (a silent fallback is how a fast path quietly stops running). **Measured, armadillo ×3 = 4,798,848 faces / 102,880 clusters, 2732×2048: 16.055 ms avg / 19.652 ms worst on indexedVertex → 13.310 ms avg / 15.831 ms worst on meshlet.** The worst frame moved from over the budget to inside it; the win is essentially all vertex reuse, since frustum culling barely helps a model that fills the viewport. **NOT done, deliberately:** cluster LOD (no simplification, so no crack-free-boundary problem — the ~20-25% gap did not need it) and BACKFACE culling, which is not an optimisation here but a product change: the Target renders double-sided (`setCullMode(.none)` + `abs()` shading), so a back face can be the visible surface of an open shell. The cones are built and carried but unused, so a watertight-gated or single-sided decision costs nothing to switch on later. **Threshold note:** the authoritative capability statement says "multi-million-tri targets" with no figure; the real fixture is 4.80M (synthetic reaches 5.24M) and no committed asset lands in a ≥5M band, so the acceptance asserts the real figure. Split out honestly: 2.2b **DEVICE ACCEPTANCE NOW HOLDS, and the earlier failures had one root cause in the HARNESS, not the product.** `renderOffscreen` allocated a fresh colour texture, depth texture and readback buffer on EVERY call (~67 MB at 2732x2048) and the 30-frame measure loop had no autorelease pool, so the process climbed from 117 MB to 4043 MB with available memory down to 1077 MB — and the first renderer was never released, carrying 2991 MB from the indexed path straight into the meshlet path so both paths' GPU buffers were resident at once. That is why `signal kill` looked intermittent: it depended on how much memory the device had free at run start. Targets are now cached per size and each frame and each path run in their own pool; peak footprint 4043 -> 2166 MB, lowest available 1077 -> 2953 MB. Crucially the same allocation was landing INSIDE the timed window, so removing it also fixed the acceptance measurement rather than the assertion being relaxed: `testMultiMillionTriangleAcceptanceOnDevice` now passes, including 4th in class where it previously read 36.45 ms. Real numbers at full iPad resolution on 4.8M triangles: meshlet 13.146 ms avg / 15.858 ms max (MET), indexed 16.629 ms avg / 20.238 ms max. **CORRECTION — every frame-time figure above was measuring render PLUS a 22 MB pixel readback, and reporting it as frame time.** `measure()` drove `renderOffscreen`, which blits the colour texture into a shared buffer in the SAME command buffer the GPU timestamps bracket (`frameProbe.attach` runs after the blit is encoded), so the probe legitimately timed the copy. No real frame performs a full-resolution readback. With a timing-only render path the true RENDER costs on armadillo x3 (4,798,848 faces) are: indexed 7.008 ms avg / 10.813 max at 1280x960 and **7.343 ms avg / 7.449 max at 2732x2048**; meshlet 5.402 / 7.870 and **6.527 / 6.604**. Consequences, stated plainly: (a) **the claim that the indexed path missed the 60 fps budget on a real asset is FALSE** — it is 7.34 ms against a 16.667 ms budget, and the "19.65 ms worst frame" that motivated changing the acceptance criterion to gate on the worst frame was readback, not render; (b) the task-0 finding that "a real asset said 16.54 ms where synthetic said 11.66 ms" compared two contaminated numbers, so its 42% overstatement figure is unreliable even though the direction (real geometry is slower) holds; (c) the meshlet path is **still faster and still worth having** — 11% at full resolution and 23% at 1280x960 — but on throughput, NOT because the alternative failed a gate. Earlier meshlet-vs-indexed deltas do not simply offset (3.48 ms then, 0.82 ms now), so the readback was not a clean constant and older comparisons should be treated as unreliable rather than shifted. Removing the readback also cut the whole perf class from ~1016 s to ~30 s (the real-asset test 493 s -> 13.3 s), which incidentally made the SIGHKILL below stop reproducing. **SIGKILL — characterised, NOT root-caused.** Five hypotheses eliminated by measurement: app memory (footprint flat across the full-resolution loop, ~2.9 GB free at every sample), process-state accumulation (a FRESH process failed identically), path specificity (it died on indexedVertex in one run and meshlet in another), GPU throughput throttling (frame times hot vs cool were 14.347 vs 14.268 ms), and thermal state alone (a full run PASSED at `thermal serious`). What remained was an intermittent kill correlated with cumulative prior GPU load — it failed when it ran last after ~520 s of load and passed when it ran first. The OS termination reason could not be captured on this host: no `devicectl console` subcommand, `log stream` has no device option, libimobiledevice absent, nothing mirrored to `~/Library/Logs/CrashReporter`, and the diagnostics archive xcodebuild collects is deleted with its staging directory. The readback removal cut the suite's sustained load ~34x and it now passes, but that reduced the EXPOSURE rather than explaining the cause, and it must not be described as fixed.

- [ ] 5.3a Interior-only singularities on a prescribed interface — the remaining half of the guarantee, and the reason the marketing claim is not yet supported. **Characterised, not merely unimplemented.** The face count at an interface vertex `b` is `n(b) − k(b)`, where `k(b)` is the number of merges across edges incident to `b`; conformance needs `k(b) = n(b) − q_in(b)`. A merge across `(b,x)` decrements BOTH endpoints, so interface vertices are coupled around the ring and every local pass deadlocks. FOUR have now been built and measured and none converged — greedy ring-first pairing (changed the failure count by EXACTLY ZERO), degree-constrained pairing, degree-pairing plus a fan lock, and (via `add-interface-singularity-guarantee`) forcing `k(b) = 0` by feature-locking every edge incident to an interface vertex. **The fourth is the most informative refutation**: the locking mechanism worked exactly as designed — `lshape` and `cross` drop to ZERO quads in the solved region, proving no merge crossed a locked edge — and conformance got strictly WORSE on every fixture at every density (`lshape` 0 -> 12 irregular, `grid66_center` 3 -> 14, `sphere_cap` 0 -> 14; best case 16 -> 16). The decomposition was wrong: `q_in(b)` counts the QUADS the surrounding cage expects, while `k(b) = 0` guarantees every region face at `b` is a TRIANGLE, so conformance would need every interface fan collapsed from the isotropic stage's 5-6 triangles to 2-3 — a large topological change, not the local flip the plan assumed. Seam quality is independently disqualifying: non-quads touching the interface rise from 0 to 12-20 at 1x and 7-8 to 43 at 4x. Evidence and a reproducible harness: `openspec/changes/add-interface-singularity-guarantee/spike/`. It is a coupled degree-constrained matching (b-matching) over the interface ring, needing a global combinatorial solver; `maximumTrianglePairing` (field_quadrangulator.cpp:195) is blossom-free. Evidence and a reproducible harness: `openspec/changes/add-weave-regional-solve/` (design.md ADDENDUM 1-2, `spike/`). **Partly mitigated — do not mistake this for the fix.** Deriving density from the prescribed boundary spacing (`RegionWeaveSolver.prescribedQuadBudget`) makes the flat and domed fixtures come out completely clean (0 irregular interface vertices, 0 seam triangles, byte-identical digests). Removed rather than built; the auto-pinning the spec does ask for belongs to 6.3's relax scrub. **The X gesture half was not a missing feature but a DESTRUCTIVE DEFECT.** `.cross` already recognized and already mapped to `.deleteFaces`, and nothing downstream knew the document stage — `Context` had no stage field, and the only "stage" in the input path is the recognizer's own two-stage pipeline. Since the viewport stays fully interactive in the UV stage by design, an X drawn there DELETED FACES from the cage being unwrapped. Proved first with a failing test (payload 265 -> 235 bytes, `pencil.deleteFaces` journaled) rather than fixed on inspection. **Shipped:** the stage rides `Context` like every other document-derived field, and ONE `nonisolated crossMeaning(in:)` switch decides what an X means — consulted by both the apply path and the alternative-swap path, because a second copy is how the chip would end up offering "Delete faces" as a one-tap alternative in a stage that does not delete. An UNSET stage is inert, not retopology: defaulting to retopology would make every context that forgot a stage silently destructive, which is the exact failure being removed. Baking is inert until Phase 7. Engine patch 0016 adds `reunwrapIsland` plus `cyber_uv_reunwrap_island` — the localized counterpart to `cyber_uv_atlas`, which re-charts and REPACKS everything and would have re-laid-out the whole model to service a gesture aimed at one region. The island is fitted back into the footprint it already occupied, **uniformly and centred**: stretching it to exactly FILL its old box scales u and v by different factors whenever the aspect changed, and that shear destroys the conformality the solve just computed — the fit would be undoing the computation it is placing. Mutation-tested (removing the fit fails the footprint test). Every other island's UVs are bitwise unchanged. **The never-unwrapped case is a REFUSAL in the engine and a POLICY in the app**, and that split is the interesting part: UVs are one per-corner column, so writing a single island into a fresh column zero-initializes every OTHER island's corners, producing a full non-null UV stream in which untouched islands read as a real layout collapsed at the origin — the absence-versus-zero trap the UV path guards everywhere else. The engine therefore refuses with `needsWholeMeshUnwrap` rather than creating the column (reported as OK-with-a-flag, not an error, since "you have not unwrapped yet" and "that face is invalid" need opposite responses), and the app routes the first X on a never-unwrapped cage to the whole-mesh unwrap. The chip names the STAGE's outcome, not the recognizer's action, so an artist is never told faces were deleted when an island was unwrapped. **NOT included:** bake-on-X (Phase 7, one case in the switch), repacking after a re-unwrap (6.6), and 2D-side gestures (6.3, no gesture surface on the panel yet). - [x] 6.5 Auto-seam proposals respecting manual seams — DONE via `add-auto-seam-proposals` (spec: uv-workflow). **A third scoping estimate of mine corrected the same way as 6.2's and 6.4's: the engine already had most of it.** `autoSeams` existed and already ran inside `unwrapAtlas`; what was missing was the ability to constrain it. Engine patch 0015 gives `AtlasOptions` a BARRIER seam set that `computeCharts` will not grow a chart across, and exposes `cyber_mesh_propose_seams`. Absent barrier is today's behaviour byte for byte, so the existing unwrap path is untouched. **The proposal is UNIONED with the barrier in the C API, and that union is load-bearing rather than cosmetic: the chart MERGE passes are not barrier-aware.** Growth respects the barrier, but a later merge can still join two charts across one, so the barrier's own edges are re-added at the boundary to make "accepting can never delete a seam you drew" a structural guarantee instead of a property of the merge heuristics. That is a real limitation stated rather than hidden: the proposal is guaranteed to CONTAIN the authored seams, but a proposal on a heavily seamed cage can still suggest a cut whose chart a merge would have unified — the guarantee is preservation, not minimality. Making the merges barrier-aware is the honest fix and is deliberately not in this change. **The proposal is VIEW state, never document state** — the same shape as the Phase 5 solver ghost but without needing `SolverGhost`, since a seam proposal is an edge set, not geometry. Accepting journals ONE `togglingSeams` over the ADDITIONS only (`togglingSeams` would SEW anything already a seam, so passing the authored set would delete exactly what the change promises to preserve); discarding journals nothing at all, which a journalled-then-undone edit would not satisfy. Proposed seams draw in AMBER against authored orange, and an edge that is already authored is excluded from the amber — drawing a proposal over the artist's own cut would imply their cut is a suggestion. **Three defects found in my own first draft, all by testing rather than reading.** (a) A proposal that finds nothing was reported as "could not analyse this mesh" — but a PLANAR cage legitimately proposes nothing (one chart, so no internal chart boundaries at all), and calling that a failure is a lie about the artist's mesh. It now says "no seams needed", with "no EditMesh" kept distinct from it; this is the same no-op-versus-failure distinction 6.1's unwrap needed, and the failing test that exposed it was failing because my FIXTURE was a flat grid, not because the code was wrong. (b) `.proposeSeams` was routed and reachable but nothing in the UI could ACCEPT, so proposing was a dead end — the same class of defect as `.autoRetopo`'s dead toolbar slot, and found the same way. A review bar in the UV panel now offers Accept and Discard explicitly. (c) The amber could never appear. `MetalViewport.updateMesh` gates its annotation refresh on `object.annotations != overlayAnnotations`, and a proposal changes no document annotation, so that comparison is always equal; and `setOverlayAnnotations` additionally gated on a non-nil annotation set, dropping the proposal for a cage with no annotations at all — the likeliest first use. Fixed with an `onSeamProposalChanged` hook, deliberately NOT `onLiveEdit`: no geometry moved, so the live-edit path's mesh re-upload would be pure cost. It fires on EVERY exit including the empty ones, so a second propose that finds nothing clears the first one's amber rather than leaving a suggestion on screen after it stopped being on offer. Both fixes were mutation-tested — reverting each makes its test fail. Engine 302/302, simulator 1394/0, device 68/68.
